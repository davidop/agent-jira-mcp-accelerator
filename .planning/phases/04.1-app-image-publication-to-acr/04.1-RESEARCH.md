# Phase 4.1 Research: App image publication to ACR

## Objective
Define a low-friction publication path for service images to ACR that is deterministic and CI-friendly.

## Findings

1. `infra/bicep/main.bicep` provisions ACR (`entagentaccelacr`) but historically did not guarantee runtime image artifacts.
2. .NET SDK container publish is suitable for this repo because there are no dedicated Dockerfiles.
3. GitHub Actions can authenticate to ACR using the existing Azure service principal session (`azure/login`) plus `az acr login`.
4. The strongest verification signal for this phase is repository/tag presence in ACR after publish.

## Recommended Strategy

1. Keep provisioning as-is for baseline Azure resources.
2. Add `actions/setup-dotnet@v4` in deploy workflow.
3. Publish each service project with `dotnet publish /t:PublishContainer`.
4. Tag images with `GITHUB_SHA`.
5. Verify repository tag existence for `agent-api`, `jira-mcp-server`, and `web`.

## Risks and Mitigations

- Risk: ACR auth context drifts.  
  Mitigation: Resolve registry and login in-step after provision.

- Risk: One service publish fails and leaves partial artifacts.  
  Mitigation: Fail-fast shell mode (`set -euo pipefail`) and per-service logging.

- Risk: Pipeline green but registry appears empty due to wrong repository naming.  
  Mitigation: Explicit repository names in publish args plus post-publish tag checks.

## Verification Commands

- `az acr repository list -n entagentaccelacr -o table`
- `az acr repository show-tags -n entagentaccelacr --repository agent-api -o table`
- `az acr repository show-tags -n entagentaccelacr --repository jira-mcp-server -o table`
- `az acr repository show-tags -n entagentaccelacr --repository web -o table`

## Exit Condition
Phase 4.1 is complete when deploy workflow produces tagged images in all three target repositories and fails otherwise.
